# Design System — Domain Glossary

## Terms

### Appearance
The user- or app-configured theme preference. Type: `'light' | 'dark' | 'system'`.
Exposed via `ThemeProvider` / `useInjectThemeProviderContext().appearance`.
`'system'` means "follow the OS preference" — it is a *setting*, not a rendered mode.

`ThemeProvider` applies `appearance` directly as a CSS class (`light` / `dark` / `system`) on its root element. Resolving `'system'` to an actual light/dark mode happens **in CSS, not JS**: the `.system` class (in `design-token-colors.css`) sets `--theme-mode: light` by default and overrides it to `--theme-mode: dark` inside `@media (prefers-color-scheme: dark)`, mirroring `.light`/`.dark`'s own token values exactly.

Because resolution already happens in CSS, JS code must never compare `appearance.value !== 'dark'` (or similar) to decide how something should look — that misclassifies `'system'` + OS-dark as light. Instead:
- For **CSS-only** visual decisions (backgrounds, colors, hiding an element), use `light:`/`dark:` Tailwind variants — these are custom `@variant`s (`tailwind-config/src/styles/index.css`) that key off the resolved `--theme-mode` custom property via `@container style(...)`, so they correctly see through `'system'`.
- For decisions that must exist as a **JS boolean** (e.g. gating a `v-if`, branching non-CSS logic), do not derive light/dark in JS. Prefer restructuring so CSS carries the light/dark distinction (see `MainLayout.vue`'s `isBranded`, which is now a pure `variant === 'branded'` check with no appearance comparison).

### Branded (variant)
A `MainLayout` `variant` option (`'branded' | 'default'`) that layers brand-colored tokens over the surface, via the `.branded` CSS class. `.branded`'s tokens are only meaningful in light mode — the class carries its own `@container style(--theme-mode: dark)` reset block so that branded content in dark mode renders identically to plain (non-branded) dark mode. This means `.branded` can be applied unconditionally whenever `variant === 'branded'`, with the light/dark distinction handled entirely by CSS, not by gating the class in JS.

### Badge — variant
A `Badge`'s `variant` prop (`ui/badge/badge.props.ts`) selects its visual weight: `'solid'` (filled background) or `'translucent'` (tinted, low-opacity background). `'outline'` is a deprecated third value — kept in the type and styles for existing consumers, but excluded from Storybook/docs and never to be used in new work. Do not add outline-only styling to future badge work.

### Badge — left config
`Badge`'s `icon?: Component | null`, `dot?: BadgeDotConfig | null`, and `avatar?: BadgeAvatarConfig | null` props are three mutually-intended-exclusive ways to render leading content, mirroring `MenuItemConfig.left`'s icon/dot/avatar/image/breadcrumbs union in `ui/menu-item/menuItem.type.ts`. Going forward, the canonical way to set leading content is the new `left?: BadgeLeftConfig | null` prop (`{ type: 'icon', icon, color? } | { type: 'dot', color? } | { type: 'avatar', name, src? }`). `icon`/`dot`/`avatar` remain as deprecated standalone props for backward compatibility; if both `left` and any of `icon`/`dot`/`avatar` are supplied, `left` wins. The standalone props are candidates for removal in a future major version once consumers migrate.

### Badge — disabled
`isDisabled` on `Badge` is purely presentational (dimmed appearance via `disabled:`-style token overrides), following the `isDisabled: boolean` half of the repo-wide `DisabledWithReason` convention (`types/disabledWithReason.type.ts`) used by `Button` and `MenuItemProps`. Badge is a non-interactive label component, so unlike `Button` it does not need `disabledReason` (no tooltip target) and does not need to alter click/hover behavior.

### Tabs — item config
`TabsItem`/`TabsRouterLinkItem`'s `icon?: Component` and `count?: number | null` props are deprecated standalone ways to render leading content and a trailing indicator, mirroring the same deprecation pattern as `Badge`'s `icon`/`dot`/`avatar` (see "Badge — left config"). The canonical way is the new `config?: TabsItemConfig | null` prop (`ui/tabs/tabs.type.ts`): `config.left` (`{ type: 'icon', icon }`, mirroring `MenuItemLeftConfig`'s discriminated-union shape) and `config.indicator` (`{ type: 'count', value } | { type: 'dot', color? }`). `config.indicator`'s `'dot'` variant is the error/attention indicator (e.g. flagging a tab containing a form error) — it reuses `UIDot` exactly as `MenuItemLeftConfig`'s `'dot'` variant and `BadgeLeftConfig`'s `'dot'` variant do, defaulting to `'error'` color rather than `Dot`'s own component default of `'gray'`, since an unconfigured attention-dot on a tab is assumed to mean "needs attention" rather than a neutral status. `config` supersedes `icon`/`count` when both are supplied. The standalone props are candidates for removal in a future major version once consumers migrate.

### DatePicker / DateRangePicker — initial placeholder
The calendar's initial placeholder (the month/day it opens on) is the `modelValue` if set, otherwise today — clamped into `[minDate, maxDate]` when that natural value falls outside the selectable range. `minDate`/`maxDate` are the *only* thing that disables a date; `getDayConfig` (`ui/date-field/dateField.type.ts`'s `DayConfig`) is purely decorative (a status dot) and never disables a day. So "the first non-disabled date" always reduces to clamping against `minDate`/`maxDate` — never a day-by-day search.
_Avoid_: "the first selectable date" without noting it's a min/max clamp, not a predicate search.

### Badge — neutral color
`'neutral'` is a `BadgeColor` unlike the other nine (`blue`/`brand`/`error`/`gray`/`moss`/`pink`/`purple`/`success`/`warning`): those are static Tailwind palette shades paired with explicit `dark:` classes per `variant`, whereas `neutral` uses theme-aware semantic tokens (`bg-primary`, `border-secondary`, `text-primary`) that already resolve correctly per theme with no `dark:` variant needed. By design, `neutral` renders identically across `outline`/`solid`/`translucent` — there is no per-variant distinction for this color. `UIDot`'s `DotColor` (`ui/dot/dot.props.ts`) was extended with `neutral` to match, since a neutral badge's dot must resolve to some color.

### DataTable (v2 table rework)
The TanStack Table-based rework of the table system, built as new components living alongside the existing `Table`/`TableRoot` (`ui/table/`) rather than replacing it in place. Existing consumers keep using the old `Table` until migrated. "DataTable" is the working name for the new component; the old component keeps the name `Table`. See [[Cell definition]], [[Column]], [[Detail pane]], [[Mobile list]] for the vocabulary introduced by the rework.

### Cell definition
A presentation-agnostic description of how one field of a row's data should be displayed. There is exactly one cell-type system — the same `Cell definition` renders in the table body, the [[Detail pane]], and the [[Mobile list]]; it is not a table-only concept. The predefined cell types are: `Timestamp`, `Text`, `Number`, `Id`, `Location`, `ContactInfo`, `Badge`, and `Custom` (via `createCustomCell`). A `Column` (see below) wraps one `Cell definition` plus table-only concerns (header label, sizing, sorting key).

Do not confuse a `Cell definition` with a TanStack `ColumnDef['cell']` render function — the latter is DataTable's internal mechanism for turning a `Cell definition` into DOM; consumers configure `Cell definition`s, not raw TanStack cell renderers.

### Column sizing — fixed pixel default per cell type, superseding fluid sizing
**Supersedes "Column sizing — fluid by default" and "Column sizing — freeze fluid width on mount/resize" below** — those entries describe the CSS `fit-content()`-driven model that this decision replaces outright, kept for history since the reasoning that led here (a real scroll-triggered width-jitter bug, fixed twice, each fix more complicated than the last) is exactly why fluid sizing was abandoned. Do not resurrect `fit-content()`/`minmax()`-based sizing without revisiting this decision.

Every column now gets a **fixed pixel width from the moment it first renders** — no browser-computed, content-dependent sizing step at all, ever. The default comes from the column's `Cell definition` **type** (`text`/`number`/`timestamp`/`id`/`location`/`contactInfo`/`badge`/`custom`), via one flat lookup table (`DATA_TABLE_CELL_DEFAULT_WIDTH_PX`, one number per type) — not derived from that cell's actual config (e.g. `Timestamp`'s `isRelative` vs `granularity`, `Id`'s `maxLength` don't change the default). A consumer whose config needs more room than the flat default overrides it explicitly via the column's `size` — now a plain `number` (pixels), replacing the old `{min, max}` CSS-unit shape outright, a breaking change to `DataTableColumnSize` made deliberately now, while nothing but the Storybook playground references the old shape.

A column's cell type was previously only knowable by calling `column.cell(item)` on a real row — there's no field that says "this is a `timestamp` column" independent of evaluating that function. That's fine for rendering (there's always a row by the time you're rendering a cell) but not for sizing, which needs an answer even with zero rows (e.g. before data has loaded). `DataTableColumn` therefore gains an explicit, required `cellType: DataTableCell['type']` field, declared once alongside `cell` — a small, mechanical addition to every column definition, but it makes "width is decided before any content exists" actually true, not just true-once-data-arrives. Do not try to derive the type from `data[0]` instead — that was considered and rejected specifically because it would make width provisional on data having loaded, defeating the point of fixed sizing.

`cell`/`cellType` are never hand-assembled separately by a consumer — see [[Column factories — createDataTableXCell]] below for how the two are kept in sync structurally rather than by convention.

This eliminates the entire class of bug the fluid model produced: there is no "measure the DOM, then decide the width" step to race against the virtualizer's own settling, no scroll-triggered jitter to freeze against, no fit-content-vs-scrollbar-vs-font-loading timing question — a column's width is a plain number known before first paint, full stop. The `dataTableColumnWidthFreeze.composable.ts` machinery (row-count-stability polling, `ResizeObserver`-triggered re-freeze, the two-bug saga documented below) is removed entirely, not adapted — there is nothing left for it to do once no column is ever fluid.

The last column still fills remaining container space (unchanged) — this is the one piece of the old fluid model kept on purpose, decided explicitly rather than defaulted into: every column except the last resolves to a fixed pixel number; the last column keeps its existing `FILL_SPACE_COLUMN`-style role, so DataTable still has no dead whitespace strip on a wide screen. Manual drag-resize (see "Column resize" entries below — those largely still apply, since dragging a fixed-width column is the same mechanism as dragging a frozen one was) still works exactly as before; the only thing that changes is where a column's width comes from *before* any drag ever happens.

### Column sizing — fluid by default, pixels only after manual resize (superseded, kept for history)
TanStack Table's `columnSizing` state is pixel-only by design (its own docs call it a "headless utility" — sizing exists to support drag-to-resize, not fluid layout; fluid/content-based sizing is explicitly left to the consumer's own CSS). DataTable's default rendering therefore does **not** read from or write to TanStack's `columnSizing` state at all — `grid-template-columns` is built directly from `DataTableColumnSize` (`min`/`max` as `rem`/`%`/`min-content`/`auto`) via plain CSS functions (`minmax()`, `fit-content()`), exactly like `TableUtil.columnSizesToGridTemplateColumns` in the current `Table`. TanStack's `columnSizing` state only gets seeded, per-column, the moment a user drags that column's resize handle — mirroring the current table's `useTableColumnWidths`, which snapshots `getBoundingClientRect()` widths into pixel state only once resizing starts. A column that has never been manually resized has no entry in `columnSizing` and stays on fluid CSS sizing.

### Column resize — TanStack provides logic only, not the handle or auto-fit
`enableColumnResizing`/`column.getCanResize()`/`header.getResizeHandler()`/`column.getSize()` give the drag-to-resize *logic* (delta tracking, clamping to `minSize`/`maxSize`, document-level mousemove/mouseup wiring) — TanStack renders no DOM. The actual grip handle (hover-revealed vertical bar on the header cell's right edge, `cursor-col-resize`) is DataTable's own markup, matching the current `Table`'s `TableHeaderCell.vue` handle exactly, for visual continuity between the two components. Double-click-to-auto-fit-to-content has no TanStack equivalent at all — same as today's `Table` (`useTableColumnResize`'s `fitColumnToContent`), it's a from-scratch measurement (render at `max-content`, read `getBoundingClientRect().width`, feed that width back in as the resized size) that DataTable re-implements independently, not something TanStack exposes.

`columnResizeMode: 'onChange'` (not the TanStack default, `'onEnd'`) — the column visibly grows/shrinks in real time as the user drags, matching the current `Table`'s hand-rolled mousemove handler and the general OS/spreadsheet mental model of drag-resize. `'onEnd'` (commit only on mouseup) is cheaper per-pixel-of-drag but needs a separate drag-preview (e.g. a guideline overlay) to avoid feeling broken while dragging — not worth building when `'onChange'`'s per-drag re-render cost is already bounded by virtualization capping rendered row count regardless of table width.

Resizing a column never grows the table past its container: the last column stays hardcoded to `FILL_SPACE_COLUMN` (fluid, `minmax(min-content, auto)`) exactly as it does with zero manual resizes — dragging column *N* narrower/wider only ever redistributes space between column *N* and the fill column, never introduces new horizontal scroll on its own. This preserves DataTable's "always fits its container by default" property; horizontal scroll still only appears from `isFirstColumnSticky`/`isLastColumnSticky` interactions, unrelated to resize.

Resize state is session-only, matching the current `Table` (`useTableColumnWidths`/`useTableColumnResize` are in-memory, reset on remount) — no localStorage persistence, no `storage-key`-style prop. Widths reset to fluid defaults on page reload. Persisting resize (like `DashboardPageDetailPane`'s width persistence) is a possible future ask, not something to build ahead of a real request.

### Column resize — first-drag jump
Found via a real bug: a column's very first resize visibly jumped a few pixels before tracking the cursor correctly; every subsequent resize of that same column was smooth. Root cause: TanStack's `header.getResizeHandler()` captures `startSize = header.getSize()` at mousedown, and `column.getSize()` falls back to `defaultColumnSizing.size` (150px, TanStack's own hardcoded default) for any column with no `columnSizing[columnId]` entry yet — which is every column DataTable has never manually resized, since fluid columns are deliberately kept out of TanStack's pixel-only `columnSizing` state (see "Column sizing — fluid by default" above). So the drag's math started from 150px while the column visually rendered at its real fluid width (e.g. 90px), producing an instant jump toward 150 on the first pixel of movement. Fixed by having `DataTableHeaderCell`'s `onResizeStart` measure the cell's actual current `getBoundingClientRect().width` and seed `columnSizing` with that real number *before* delegating to `header.getResizeHandler()(event)` — `table.setColumnSizing`'s underlying ref write is synchronous, so `header.getSize()` reads the real width on the very same call, not a stale/default one. Once a column has a real `columnSizing` entry, every later resize of it is unaffected — this only ever showed up on a column's first drag.

### Column resize — minimum width
Found via a real bug: TanStack's own resize floor (`defaultColumnSizing.minSize = 20`) is small enough that a column could be dragged almost fully behind its neighbor, hiding its own header label — bad UX, not a TanStack misconfiguration on our part, just a default that assumes the consumer sets a real `minSize` (which DataTable's column defs never did, since fluid sizing is handled outside TanStack entirely).

The resolved floor is two-layered, in this order:
1. **`DATA_TABLE_MIN_COLUMN_WIDTH_PX`** (a fixed constant, `utils/dataTable.util.ts`) — the absolute floor every column respects, regardless of its label or declared size. No column can ever be dragged below this, full stop.
2. **Per-column ceiling-raiser, never a lowerer** (`DataTableUtil.resolveColumnMinResizeWidthPx`) — if the column declares `size.min` as a fixed unit (`rem`), convert it to pixels; otherwise (`min-content`/`auto`/`%`, or no `size` declared — the common case, since no column in the playground declares one) fall back to that column's *measured* natural content width. Whichever of these is larger than the constant becomes that column's actual floor — a column with a long label (e.g. "Last active") gets a bigger effective minimum than the bare constant; a column with a short label (e.g. "ID") just uses the constant.

The measurement itself (for the `min-content`/`auto`/`%`/undeclared fallback) happens once, on mount, in `DataTableHeaderCell` — reading the sort button's `scrollWidth` (not `getBoundingClientRect().width`, and not the `max-content`-reflow trick `onResizeFitToContent` uses) directly, since `scrollWidth` reports the button's true content width even if it were ever visually clipped. This is registered once per column and fed into `columnDefs`' `minSize` reactively — no drag-time remeasurement, since a column's label doesn't change while dragging it.

**Gotcha that broke the first implementation attempt**: setting `columnDef.minSize` alone does nothing to what actually renders. TanStack's drag handler writes an *unclamped* raw number straight into `columnSizing` state (`updateOffset`'s `newColumnSizing[columnId] = headerSize + headerSize * deltaPercentage`, no `minSize` involved) — the `minSize`/`maxSize` clamp only exists inside `column.getSize()`'s *read-time* computation. DataTable's `gridTemplateColumns` was reading `columnSizing.value[column.key]` directly (the raw, unclamped stored value) instead of calling `table.getColumn(column.key)?.getSize()` (which applies the clamp) — so the floor was correctly configured but silently never enforced anywhere. Always read a resized column's width via `getSize()`, never the raw `columnSizing` state object, when `minSize`/`maxSize` need to apply.

The two rejected simpler alternatives, for the record: a single flat constant with no per-column logic (rejected — a long label could still be clipped if the constant happens to be smaller than that label's natural width, the exact bug this exists to prevent) and a purely per-column measured/declared floor with no absolute constant underneath (rejected in favor of always having a hard floor, per explicit ask, rather than trusting measurement alone in every case e.g. an icon-only header with no text).

### Column resize — handle centered on the column boundary
Found via a real bug: the resize handle's hit area (`absolute right-0 w-4`) sat entirely inside its own column, so the visible grip — centered within that hit area — rendered visibly offset to the left of the true boundary between columns, not straddling it. Fixed with `translate-x-1/2` on the hit-area box, shifting it right by half its own width so it's centered exactly on the boundary (half inside this column, half inside the next). The old `Table`'s `TableHeaderCell.vue` has the identical un-shifted markup and the same visual offset — this was a pre-existing quirk in the component this was ported from, not something specific to DataTable's layout, and was deliberately fixed here rather than faithfully reproduced.

Centering the handle on the boundary means it now paints partly outside its own header cell's box, which surfaced a second, previously-latent issue: the header cell's root `overflow-hidden` (there only to truncate a long label) was clipping that overflow. Fixed by scoping `overflow-hidden`/`truncate` to just the label button, not the whole cell root — the cell root itself no longer clips anything, so the handle can render past its own edge. This in turn exposed a third: once unclipped, the *next* column's header cell (painting later in DOM order, same implicit stacking level) visually covered the handle's overflowing half.

First attempt at the z-index fix was `hover:z-40` on the whole cell root — wrong trigger. Hovering *anywhere* in a cell (its label, its sort icon, anywhere) promoted it, so moving from column N's handle into column N+1's plain label area (nowhere near N+1's own handle) still flipped which cell was on top, producing a visible flicker at the boundary unrelated to any actual resize interaction. Fixed by narrowing the trigger to `has-[.cursor-col-resize:hover]:z-40` (only *this* cell's own handle being hovered elevates it) plus a `z-40` bound to `isResizing` (so elevation persists for the whole drag, not just up to the moment the cursor crosses into the next column) — hovering a neighboring cell's non-handle content now does nothing.

### Column sizing — freeze fluid width on mount/resize, never on scroll (superseded, kept for history)
**Superseded by "Column sizing — fixed pixel default per cell type" above.** This entire freeze mechanism (and the composable it describes) is deleted, not kept — every column has a fixed pixel width from first paint now, so there is no fluid width to ever freeze.

Found via a real bug: a fluid (never manually resized) column's width is CSS `fit-content()` — the browser's own layout engine, re-evaluated live over whatever rows are *currently mounted in the DOM*. Since virtualization only ever mounts a subset of rows, scrolling to a different window of rows (some with wider/narrower content in that column, e.g. `Timestamp`'s relative-vs-absolute rendering, or `ContactInfo`'s variable-length email/phone) changes what `fit-content()` sees, and the column visibly resizes — then resizes back when scrolling back to the original rows. Confirmed with Playwright: scrolling through the "Last active" and "Contact" columns shifted them by 50+ px purely from scroll position, with no data or resize interaction at all.

The fix keeps a fluid column fluid on first paint, then locks it: each fluid column's *live* rendered width (from whichever rows are visible at that moment) gets measured and written into the same `columnSizing` state a manual drag-resize would populate — same mechanism, just triggered automatically instead of by a user drag. Once a column has a `columnSizing` entry, `gridTemplateColumns` already treats it as pixel-fixed (see "Column resize" above) — scrolling afterward mounts/unmounts different rows, but the column's grid track is now a fixed number, not `fit-content()`, so it can't be moved by what happens to be mounted.

This only ever measures **currently-visible** rows, never the full dataset (see "Column resize — minimum width" for why measuring an off-screen row's content isn't attempted elsewhere either — same reasoning: `fit-content()` never saw the whole dataset either, this only freezes whatever it happened to already be showing). A column that's momentarily narrower than some later, off-screen row's content will only clip that row's content once it scrolls into view — a tradeoff, not a regression, since the pre-fix behavior already had *some* row on screen shrink/grow the column arbitrarily depending on scroll position; freezing just stops that shrinking/growing rather than guaranteeing every row's content always fits.

The freeze re-runs on the table's own container resizing (via `ResizeObserver` on `scrollContainerEl`, not on window resize specifically — matches the container-query-driven mobile breakpoint's existing "react to this DataTable's own rendered width" convention, see "Mobile list — breakpoint trigger") — a genuine layout change (e.g. a detail pane opening and narrowing the table) re-measures once against whatever's visible in the new width. Scrolling alone never re-triggers a fresh freeze; only a real container-width change does.

**Two gotchas that broke the first implementation attempt.** First, the loop order: freezing column 1 changes its grid track from `fit-content()` to a fixed pixel value, which reflows the *whole* grid immediately — so measuring column 2 right after (in the same synchronous loop) reads its width in an already-partially-frozen layout, not the original fully-fluid one. Fixed by measuring every column's width into a plain array first, then applying all the `setColumnSize` writes only after every measurement is captured — no column's measurement can be corrupted by an earlier one's freeze.

Second — the actual cause of the visible bug (every header truncated, e.g. "Name" → "Na…", on first load; confirmed still wrong even after the loop-order fix above) — was a race against the *virtualizer's own* initial sizing pass, not a resize-observer-fires-twice issue (that was a wrong theory chased first and ruled out: an explicit delay of up to 500ms made no difference, proving it wasn't timing in the naive sense). `useDataTableVirtualScroller`/`useDataTableGroupedVirtualScroller` renders far fewer rows on its very first pass than actually fit the container (confirmed via direct instrumentation: 8 rows instead of the eventual 21) until its *own* `ResizeObserver` on the same scroll container corrects it. This freeze composable's `ResizeObserver` observes that identical element, and its guaranteed first callback was winning the race against the virtualizer's correction — so the initial freeze measured `fit-content()` over only 8 rows' worth of content, locking in widths too small for the eventual full row set. Fixed by not trusting the first callback blindly: before the *initial* freeze specifically, poll the rendered `[role="row"]` count every 50ms (capped at 20 attempts) until two consecutive polls agree, then measure — a genuine stability check on the actual signal that matters (rendered row count), not an arbitrary fixed delay. Every *later* callback (a real container resize, not the initial mount) freezes immediately, since the virtualizer is already fully settled from prior renders by then and this race can't recur.

### Timestamp cell — relative vs. granularity
A `Timestamp` cell definition takes either `{ isRelative: true }` (renders as "3 hours ago", recomputed live) or `{ granularity: 'second' | 'minute' | 'hour' | 'day' | 'month' | 'year' }` (renders an absolute date/time truncated to that unit) — never both. This is a discriminated union, not two independent flags: relative time already implies its own precision, so pairing it with a granularity is meaningless and rejected at the type level.

### Column factories — createDataTableXCell
One factory per `Cell definition` type (`createDataTableTextCell`, `createDataTableNumberCell`, `createDataTableIdCell`, `createDataTableLocationCell`, `createDataTableContactInfoCell`, `createDataTableBadgeCell`, `createDataTableTimestampCell`, `createDataTableCustomCell`), each returning a complete `DataTableColumn` — this is the only supported way to author a column. A consumer never writes `cell`/`cellType` as two separate object fields; each factory is monomorphic (its `cellType` is a hardcoded literal, its `value` option is typed to exactly that cell type's own shape), so `cell` and `cellType` come from the same function call and cannot drift apart the way independently-typed sibling fields could. This replaces an earlier "keep them in sync by convention" comment on `DataTableColumn.cellType` — there is no longer a convention to violate, since there's nothing left for a consumer to keep in sync by hand.

Every factory shares the same base shape — `{ headerLabel, key, size?, value: (item: TItem) => <ThatCell'sOwnFields> }` — where `value` is a function of the row returning exactly the fields that cell type's own interface declares (e.g. `createDataTableTextCell`'s `value` returns `{ value, fallback? }`; `createDataTableBadgeCell`'s returns `{ label, color?, left?, rounded?, size?, variant? }`). `createDataTableCustomCell` additionally takes a `config: DataTableCustomCellConfig<TValue>` (the render/detail components), separate from `value`, mirroring `createCustomCell`'s existing split between cell-rendering config and per-row value.

### Column vs. Cell definition
A `Column` is table-specific: it pairs a [[Cell definition]] with header metadata (label, description), sizing, and sort key. The `Cell definition` itself carries none of that — it only knows how to render a value. This split is what lets the same `Cell definition` be reused in the [[Detail pane]] (which has no header row) and the [[Mobile list]] (which has no columns and, per [[Mobile slot — API location]], no per-column mobile config either — mobile placement is a separate `mobileCard` prop, not a `Column` field).

### Detail pane
A side panel that shows every [[Cell definition]] for one row, including columns hidden from the table itself, auto-generated from the row's `Column`/`Cell definition` set — not a separately authored schema. Closed with Escape or a close button. `Cmd+O` navigates to the row's actual detail page, reusing the same `row(item).onClick` used for whole-row navigation elsewhere in DataTable (see [[Row actions (row prop) — row-scoped adapter into the Action registry, shipped Phase D]]) — there is no separate "detail pane link" prop. See [[Active row]] for what row Spacebar/arrow keys act on, and [[Detail pane — hover vs. arrow-key asymmetry]] for why hovering and arrow-navigating behave differently once the pane is open.

Desktop-only: this is a mouse-and-keyboard interaction model with no touch equivalent. The [[Mobile list]]'s own tap-to-expand + "Go to detail" link already covers the same underlying need (seeing hidden columns, navigating to the real detail page) in a touch-appropriate way — there is no separate mobile detail pane.

When the table is grouped, arrow up/down skip over group header rows entirely and only ever land on real data rows — a group header has no single row's `Cell definition` set to show, so there is nothing meaningful to stop on.

### Detail pane — built on DashboardPageDetailPane
DataTable's detail pane renders its row content *through* the existing `DashboardPageDetailPane` (`ui/dashboard-page/detail-pane/`), rather than a self-built panel — see `docs/adr/0003-detail-pane-reuses-dashboard-page.md` for the full reasoning. Practical consequence: DataTable's Spacebar/detail-pane feature expects to be rendered inside a `DashboardPage`, which is the component that actually calls `useDetailPane()`/`useProvideDetailPaneContext()` and registers into the app-shell-level `MainContentDetailPaneContext` (so the app's `TopBar` can render a global toggle for it). This is not a general constraint on DataTable itself — DataTable still works standalone anywhere (a dialog, a card, a page with no `DashboardPage`) — it's specific to whether the *detail pane* feature is active; a DataTable used outside a `DashboardPage` simply shouldn't enable it.

**Phase 4 implementation is paused** (not started beyond this design work). Reason: `DetailPaneContext` is plain provide/inject, not slot-scoped, so `DataTable` *can* control open/close/active-row state by injecting it directly — but the pane's rendered *content* still has to be placed by the app author via `DashboardPage`'s own `#detail-pane` slot, since `DataTable` cannot inject content into a sibling slot it doesn't own. The resulting API shape (`DataTable` + a separately-exposed `UIDataTableDetailPaneContent` component wired via a template `ref` handoff between siblings) felt too manual and disjointed to ship as-is. This confirmed the tracked future refactor above is worth doing *before* Phase 4, not after — extracting `DashboardPageDetailPane`'s core mechanics into a standalone primitive first should let `DataTable` own its detail pane as a single cohesive piece, rather than exposing this two-piece wiring to every consumer. Sequencing: finish the remaining phases, then revisit the standalone-panel extraction, then build Phase 4 on top of it.

**Tracked future refactor**: extract `DashboardPageDetailPane`'s core mechanics (`useDetailPane`'s open/close/resize/persistence state, the sliding-panel transition) into a standalone primitive that both `DashboardPage` and `DataTable` depend on directly, rather than `DataTable` depending on `DashboardPage` to get there. This would remove the `DashboardPage`-ancestor expectation above entirely. Not done now because it means carving apart currently-intertwined code (`DashboardPage.vue` is both the state owner and the `MainContentDetailPaneContext` registrant) without a second real consumer yet to validate the split — worth doing once DataTable's detail pane has shipped and this coupling has actually been felt in practice, not speculatively upfront.

### Active row
A single shared "current row" pointer, distinct from real DOM/browser focus, moved by two independent inputs that each overwrite the other's result — whichever acted most recently wins:
- **Hovering a row** with the mouse sets it as the active row (visually indicated), but does **not** by itself open or update the detail pane.
- **Arrow up/down**, only while the detail pane is already open, move the active row to the previous/next row in the current row order.

Moving the mouse *off* the table entirely (e.g. onto the detail pane itself, to click its close button or a `Cmd+O` link) does **not** clear or change the active row — it only changes when a *different table row* is actually hovered. This is what lets someone interact with the open pane's own controls without accidentally losing or shifting "current row."

### Detail pane — hover vs. arrow-key asymmetry
Spacebar is the only thing that **opens** the detail pane, and it opens it for whatever the [[Active row]] is at that moment (i.e. wherever the mouse was last hovering, or wherever arrows had last moved it while some other instance of the pane was open). Once the pane is open, the two inputs that move the active row behave asymmetrically on purpose:
- Hovering a new row moves the active-row indicator but does **not** update the open pane's content — Spacebar must be pressed again to commit that row into the pane. This exists specifically so idle mouse movement (e.g. moving toward a button, or passing over other rows while reading) can never silently change what the pane is showing.
- Arrow up/down, once the pane is already open, immediately move the active row **and** update the pane's content in the same keypress — no extra confirmation. Arrow presses are always a deliberate, discrete action (unlike ambient mouse movement), so they don't need the same guard hover does.

### Grouping vs. Sub component (row expansion)
DataTable has two distinct expand/collapse mechanisms, not one:
- **Grouping**: rows are aggregated under a shared group key and collapse under a group header row (the existing `TableGroupedData`/`TableSubGroupedData` concept, ported to TanStack's grouping row model).
- **Sub component**: a single row reveals arbitrary extra content beneath itself when expanded (e.g. an expand chevron), independent of any grouping — this row is not sharing its expansion state with sibling rows.
These are orthogonal: a grouped table's individual rows can still each have their own sub component.

### Sub component — API shape
A single prop, `subComponent?: (item: TItem) => Component | null`. Returning `null` for a given row means that row has no expand chevron at all — not merely an empty expanded area. There is deliberately no separate `getRowCanExpand`-style predicate prop (mirroring TanStack's own split more literally): the null-return already communicates "not expandable," so a second prop would be redundant. This mirrors `DataTableColumn.cell`'s own shape (a function of the row item returning what to render).

`hasSubComponent` (whether the expand column exists at all, reserving grid space and rendering the leading header cell) is derived from whether **any row's actual return value** is non-null (`subComponentByItemKey.value.size > 0` in `DataTable.vue`) — not from whether `props.subComponent` is merely set to a non-null function. A consumer that always passes a real function reference but has that function return `null` for every row (e.g. gated behind some other flag) must not see a reserved, empty leading column — this bit the first Storybook story built for it. `subComponentByItemKey` is computed directly from `props.data`, deliberately independent of TanStack's `table`/row model, to avoid a circular dependency (`hasSubComponent` feeds into `useDataTable`'s grid-template calculation, which constructs `table` in the first place).

### Row selection state
DataTable reuses the existing `TableSelectionState<T>` shape from the current table verbatim: `{ type: 'includes' | 'excludes', items: T[] }`. This is a deliberate consistency choice — do not introduce a differently-named shape (e.g. `type: 'include' | 'exclude'`, `values: [...]`) for DataTable's selection emit.

### Selection action bar — old table's version doesn't exist
The current `Table`'s `TableRootProps.actionGroup` documentation claims a "floating action bar displayed when rows are selected," but no such UI actually exists anywhere in `ui/table/` — `actionGroup` only ever feeds into an internal `createAction({ group: actionGroup })` call for column auto-fit, never rendered as a bar. DataTable's `DataTableSelectionActionBar.vue` is a from-scratch component, not a port. It renders `selectionActions: Action[]` (a real action array, unlike `ActionGroup` which has no `actions` field) filtered through `resolveApplicable`.

### Storybook actions need `availableWhenUnauthenticated: true`
`resolveApplicable()` (`@wisemen/vue-core-actions`) returns `false` for any action lacking `availableWhenUnauthenticated: true` whenever `isAuthenticated.value` is falsy — which it always is in Storybook (no real auth store). Any `Action` used in a DataTable/design-system story (e.g. `selectionActions`) must set `availableWhenUnauthenticated: true` or it will silently never appear, with no error — this bit the first `DataTableSelectionActionBar` story and is easy to hit again.

### Grouping vs. sub component — state implementation
TanStack Table's grouping and expansion features share a single `expanded: ExpandedState` bucket (a `Record<rowId, boolean>`), toggled via the same `row.toggleExpanded()`/`row.getIsExpanded()` on every row regardless of whether that row is a synthetic group-header row or a plain data row — there is no built-in separation between "this group is collapsed" and "this row's sub component is open." Row ids never collide in practice (group rows get synthetic ids like `status:active`, prefixed by parent group id; data rows keep their own `getRowId` value), so nothing breaks by accident — but DataTable does not rely on that non-collision. [[Grouping vs. Sub component (row expansion)]] are kept genuinely independent in the implementation: TanStack's `expanded` state is used **only** for group-row collapse (via `getGroupedRowModel()` + `getExpandedRowModel()`), while sub-component open/closed state is a separate, local `Set<rowId>` outside TanStack entirely, with the sub-component's detail row rendered manually by DataTable rather than via TanStack `subRows`. This avoids `toggleAllRowsExpanded()`/`expanded: true` (the "expand everything" shorthand) ever accidentally opening sub-components when a consumer just meant "expand all groups," or vice versa.

### Grouping — API shape
DataTable groups the TanStack-native way: consumers always pass flat `data: TItem[]` plus an optional `groupBy` column key, and rows aggregate automatically by that column's value — there is no pre-grouped data shape to construct (unlike the old `Table`'s `TableGroupedData<T>[]`, which required the consumer to wrap rows into groups with an explicit label themselves). The group header's label is derived directly from the grouped value (formatted through that column's own `Cell definition`, so a `groupBy` on a `Badge` or `Timestamp` column renders its group header the same way the cell itself would render that value) — there is no separate "group label" string to author.

### Grouping — accessor derivation
A `Column`'s `cell: (item) => DataTableCell` only knows how to *render* a value — it has no separate declared accessor for the raw property it reads. TanStack's grouping (and its underlying `accessorFn`) needs a real per-row scalar to bucket rows by, so DataTable derives it by calling `column.cell(item)` and extracting a scalar from whichever `Cell definition` fields make sense per type (`Text`/`Number`/`Id` → `value`; `Timestamp` → `value.epochMilliseconds`; `Badge` → `label`; `Location` → the field matching its own `precision`), in `getDataTableCellGroupingValue` (`utils/dataTableCellGroupingValue.util.ts`). `ContactInfo` and `Custom` cells have no single scalar and return `null` for every row — grouping by one of these columns puts every row in one group rather than throwing. Do not add an explicit `accessor` field to `DataTableColumn` to solve this differently without revisiting this decision — it was chosen deliberately to avoid a column API change.

### Grouping — up to two levels
TanStack's grouping engine (`getGroupedRowModel`) natively supports arbitrary nesting depth via `grouping: string[]`, one column id per level — DataTable exposes exactly two of those levels, matching the old `Table`'s `TableGroupedData`/`TableSubGroupedData` split (group + sub-group, no deeper). `groupBy` accepts `string | [string, string] | null`. A single string is one level; a two-element tuple groups by the first key, then sub-groups within each group by the second key. There is no third level — if a consumer needs deeper nesting, that's a deliberate scope boundary to revisit explicitly, not an oversight.

### Grouping — column order
TanStack's `groupedColumnMode` defaults to `'reorder'`, which silently moves the grouped-by column to the front of `getVisibleLeafColumns()`/`getFlatHeaders()`/every leaf-column list — a default aimed at libraries that show the grouped column as the *first, always-visible* column (spreadsheet-style grouping UIs). DataTable sets `groupedColumnMode: false` explicitly, because it already renders its own dedicated group-header row (`DataTableGroupRow`/`DataTableMobileGroupHeader`) — it has no use for TanStack additionally reordering the flat data columns, and the reorder actively breaks anything that binds a rendered column position to a `Header`/`Column` object by array index (header cells, resize handles) once grouping is active, desyncing visual position from underlying column identity. Found via a real bug: dragging a header cell's resize handle resized the *wrong* column whenever `groupBy` was set — traced to `getFlatHeaders()[i]` no longer matching the visually-rendered `i`th header once grouping silently reordered the array.

### Row drag & drop — benched, likely a separate component
Explored during grilling, then benched: no current project has an actual row-DnD use case, so this isn't being designed against a real requirement yet.

The key finding worth preserving: drag-to-reorder and DataTable's `sort` prop are two mutually exclusive models of *who owns row order* — `sort` means the server/sort-key decides order (index-API-shaped tables: users, invoices, anything paginated/filtered), drag means the user decides order and that order **is** the data (kanban-as-table, curated sequences, explicit-`position`-field tables). A table only has a legitimate drag-to-reorder use case when there'd be no other way for the user to express "put this one first" — if sort/filter already answers "what order," adding drag on top is a second, conflicting mechanism for the same concern.

This pulls in a different enough direction from DataTable's current shape — order-authority model, virtualization relevance (drag use cases are typically small, hand-curated lists; DataTable's virtualization work targets large sort/paginate-driven datasets), and grouping semantics (drag's "which group is this in" is row *data*; DataTable's grouping is a *view* over already-loaded data) — that bolting an `isDraggable` mode onto `DataTable` itself was rejected in favor of: if/when a real use case shows up, build a **separate component** (working name `DataTableOrderable`) that shares DataTable's cell definitions, column/mobile-list machinery, and selection mechanics, but has no `sort` prop and its own row-ordering/grouping rules (including cross-group drag, which `DataTable` itself will never support — see reasoning below). Do not add drag props to `DataTable`'s own API without revisiting this.

Reasoning on cross-group drag, preserved from the original scoping (still applies to a future `DataTableOrderable`): a cross-group move means the row's group-defining field actually changes (e.g. reassigning an invoice's `recipient`), which is a data mutation requiring a consumer API call and rollback handling, not a pure client-side reorder — so it needs deliberate design, not a default assumption either way.

### Grouped virtualization
Desktop's grouped branch is virtualized the same way the flat/ungrouped branch is, via a second composable (`useDataTableGroupedVirtualScroller`, alongside the flat-list `useDataTableVirtualScroller`) — not a shared one, because group-header rows and data rows have different real heights, so a single fixed `estimateSize` (fine for the flat list, where every row is the same height) would misplace every row after the first group header. The grouped scroller uses TanStack Virtual's dynamic measurement (`measureElement`, wired via a `ref` callback + `data-index` attribute in the template) with a per-row-type `estimateSize` guess (36px group header, 40px data row) as the initial layout before the real DOM element is measured.

This relies on a TanStack Table default that's easy to miss: `paginateExpandedRows` (default `true`) means `table.getRowModel().rows` is *already* a flat, display-order sequence — group headers interleaved with data rows, collapsed groups' children already excluded. No separate flattening step was needed; the existing row model was already virtualization-ready.

Row identity for the virtualizer's internal size cache must be the row's own stable id (`getItemKey` → `row.id`), not its array index — collapsing a group removes rows from the middle of the array and shifts every later index, which would otherwise silently hand a newly-shifted-in row the previous occupant's cached size.

### Mobile list — virtualized
The mobile card list is virtualized (`dataTableMobileVirtualScroller.composable.ts`), mirroring the desktop grouped case's dynamic-measurement approach rather than flat's fixed `estimateSize` — mobile has the same group-header-vs-data-row height difference as grouped desktop, plus a card's own height changes in place on expand/collapse, which a fixed estimate can't account for. `measureElement`'s underlying `ResizeObserver` re-measures automatically when a mounted card's height changes, since only the expanded content inside `DataTableMobileCard`'s root toggles — the measured element itself never unmounts across the toggle.

This required giving `DataTableMobileList` its own scroll container (`overflow-auto`, sized via `max-h-full` against a `flex-1 min-h-0` slot in `DataTable.vue`'s root) — previously the mobile list rendered inline and grew with page content, since virtualization requires a real scrollable ancestor to measure against. A consumer that relied on page-level scroll for the mobile list (rather than giving `DataTable` a bounded height) will see this container clip/scroll internally instead — this is the same model desktop's `scrollContainerEl` already used, so it's parity, not a new constraint, but it's the one behavior change worth flagging if a consumer's layout assumed unbounded natural height on mobile.

### Row view model — shared between desktop and mobile
`DataTableRowViewModel<TItem>` (`types/dataTableRowViewModel.type.ts`) is the single per-row shape both `DataTable.vue`'s desktop grid and `DataTableMobileList.vue` render from — `isGrouped`, `groupLabel`/`groupLabelCell`, group selection booleans, the underlying TanStack `row`, sub-component state. It's computed once in `DataTable.vue` (from `table.getRowModel().rows`) and passed down, so grouping/selection derivation exists in exactly one place regardless of which presentation is active.

### Mobile list
The responsive transformation of DataTable below a breakpoint: rows render as a two-line, two-column card (Apple Mail-style) instead of a grid row, with the remaining column data revealed on expand. Selection is off by default on mobile and must be turned on via an explicit toggle button, which then reveals a checkbox on each list item — this differs from desktop, where the checkbox column is always visible whenever `isSelectable` is true.

Grouped mobile list: `groupBy` group boundaries render as collapsible section headers (`DataTableMobileGroupHeader`) interleaved with cards, mirroring the desktop `DataTableGroupRow` — same collapse/select-all-in-group behavior, just laid out as a plain block list instead of a subgrid row. Both `DataTable.vue` and `DataTableMobileList.vue` consume the same `DataTableRowViewModel<TItem>[]` (see [[Row view model — shared between desktop and mobile]]) so grouping logic is derived once, not reimplemented per presentation. Virtualized — see [[Mobile list — virtualized]].

### Mobile slot
The mobile card's collapsed view has 4 named positions: `primary` (top-left, the row's main label — required), `secondary` (bottom-left, supporting text), `meta` (top-right, e.g. a timestamp), `indicator` (bottom-right, e.g. a status dot or badge). Every column not named in one of these positions renders in the expanded card instead (see [[Mobile slot — API location]] for where these positions are actually configured). This 4-slot naming is an explicit decision from the grilling session — not to be overridden by visual mockups (see [[Visual reference — mobile list prototype]]).

### Visual reference — mobile list prototype
A Claude-generated visual-only prototype (`Table mobile transformation 2/Mobile Table Transformation.dc.html`, invoice-list example on the "Crispy" ERP UI kit) exists to sanity-check visual layout — it is reference material for look-and-feel, not a source of settled decisions. Its slot naming (`primary/secondary/trailing/detail`) and defaults do **not** supersede [[Mobile slot]] above. Interaction ideas worth evaluating from it, not yet adopted: swipe-left-to-reveal quick row actions (iOS Mail pattern) as a mobile-native replacement for the desktop `⋯` popover, a bottom action sheet for the remaining overflow actions, toast confirmations after destructive actions, and sticky collapsible group headers carrying a running subtotal on the grouped mobile list. Treat these as candidates to discuss, not requirements.

### Mobile list — breakpoint trigger
The desktop-grid-vs-mobile-card switch is a pure CSS container query on DataTable's own rendered width, not a JS-computed `isMobile` prop and not a viewport media query. Matches the existing container-query convention in this codebase (`@container/name` + `@md/name:` variants, e.g. `FormFieldGrid.vue`) — `container-type: inline-size` declared once on DataTable's root (`@container/data-table`), with the mobile-card layout activating below that container's own width threshold, not the browser viewport's. This means DataTable renders correctly as a mobile list even when embedded in a narrow panel on a wide desktop screen, and as a normal grid in a wide embed on a narrow device — deliberately decoupled from screen size.

### Mobile slot — API location
Lives on `DataTableProps` as a single dedicated `mobileCard?: { primary: TKey, secondary?: TKey, meta?: TKey, indicator?: TKey }`, referencing column keys — **not** on `DataTableColumn` itself. This reverses an earlier decision (`mobile?: { slot }` per-column) made during initial implementation: with per-column slot flags, nothing owned or validated "the card's shape" as a whole, so two columns silently claiming the same slot meant one's data silently disappeared on mobile with no error, since the mapping was reconstructed by scanning all columns for slot claims rather than being one first-class object. `mobileCard` makes that collision structurally impossible — each of the 4 positions is a single named field, not a value multiple columns can each claim. Any column key not referenced by `mobileCard` renders in the expanded card instead, so `DataTableColumn` carries no mobile-specific field at all.

### Nested layer count
`DialogContext` (`ui/dialog/dialog.context.ts`) tracks how many popover-family descendants (`Popover`, `Autocomplete`) are currently open inside a given `Dialog` instance — incremented/decremented by that descendant via `useRegisterAsDialogNestedLayer()` (`ui/dialog/dialogNestedLayer.composable.ts`) on open/close, a no-op if it isn't rendered inside any `Dialog`. This exists so a `Dialog`'s own outside-click handling can defer to a still-open nested popover instead of dismissing at the same time as it — see `docs/adr/0004-dialog-defers-to-nested-popover-on-outside-click.md`. Do not confuse this with [[DismissableLayer stack]] below — this is a small, purpose-built counter, not an attempt to reimplement Reka's real layer ordering.

### DismissableLayer stack
The shared mechanism every dismissible floating/overlay component in this design system sits on top of, via reka-ui: `Dialog`'s `RekaDialogContent`, `Popover`'s `RekaPopoverContent`, and `Autocomplete`'s `RekaComboboxContent` (confirmed identical wrapper internals via `ComboboxContentImpl.js`) are all, underneath, one `DismissableLayer` component (`reka-ui/dist/DismissableLayer/DismissableLayer.js`) backed by one module-level registry (`context.layersRoot`, a `Set` of currently-mounted layer elements). Escape-key dismissal already consults this registry (only the topmost layer dismisses on Escape) — outside-pointerdown dismissal does not, which is the root cause behind [[Nested layer count]]'s ADR. `context` is not exported from reka-ui's public API — our code cannot read Reka's real layer order directly, which is why [[Nested layer count]] is a separate, purpose-built counter rather than a wrapper around this one.

### getLink — added ahead of the detail pane, later removed (superseded by row(), Phase D)
`DataTableProps.getLink?: (item: TItem) => RegisteredRouteLocationRaw | null` was added during mobile list work (Phase 5), before `row` existed — see [[Row actions (row prop) — row-scoped adapter into the Action registry, shipped Phase D]] for what replaced it. Removed outright, not deprecated, when `row` shipped: the new `DataTable` had zero real consumers anywhere in the repo at that point (only its own Storybook story), so there was nothing to migrate gradually.

### Sticky columns — currently first/last only, by boolean, not by arbitrary key
Today's mechanism (`isFirstColumnSticky`/`isLastColumnSticky`, `useDataTable`'s `pinFirstColumn`/`pinLastColumn`) is real TanStack column pinning (`ColumnPinningState`), not a CSS hack — but it only ever pins exactly one column on each side, and both default to `false`. A later ask ("first column sticky by default" + "pin any column by key") is two separable changes, not one: flipping `isFirstColumnSticky`'s default is a one-line change with a real visual consequence for any consumer whose first column isn't a natural "identity" column (e.g. a `Badge`); pinning an *arbitrary* column by key is a bigger change, since TanStack's `columnPinning.left`/`.right` already accept an array of column ids — DataTable's `gridTemplateColumns`/CSS `sticky left-0`/`right-0` positioning does not, today, compute a cumulative left/right offset for more than one pinned column per side (`DataTableHeaderCell.vue`/`DataTableCell.vue` both hardcode `left-0`/`right-0`, assuming exactly one sticky column exists per side). Do not ship "sticky by key" without also generalizing the offset calculation past the single-column assumption.

### Row actions (`row` prop) — row-scoped adapter into the Action registry, shipped Phase D
See `docs/adr/0005-data-table-row-actions-bypass-action-registry.md` for the full decision history (an earlier revision proposed plain, registry-decoupled objects — superseded; a Phase D re-grilling re-verified the decision still held before implementation — see the ADR's own append). Shipped shape: `row?: (item: TItem) => { onClick?: () => void, model: RegisteredActionContext['models'][number], actions: { inline: Action[], more: Action[] } } | null` (the `| null` on the whole return, not just `onClick`, was added during implementation — a row can have no click target/actions at all). `actions.inline`/`actions.more` are real `Action` objects; `model` replaces the old standalone `getActionModel` prop. `inline` renders as always-visible icon buttons (via `UIActionTrigger`, the existing single-action slot-wrapper — not hand-rolled icon/label resolution, see [[Inline action rendering — reused UIActionTrigger, did not hand-resolve Action fields]]); `more` renders behind a `⋯` overflow menu in the same trailing `DataTableRowActionsCell`, and also feeds the row's right-click context menu. `onClick` supersedes `getLink`/`onRowClick` — note `onRowClick` never actually existed on the new `DataTable`'s props at all (it's purely an old-`Table` concept); only `getLink`/`getActionModel` needed removing. Both were removed outright, not deprecated — the new `DataTable` had zero real consumers when `row` shipped.

### Whole-row click — per-cell click-catcher, not one row-level overlay
First implementation attempt was wrong: a single `pointer-events-none` button spanning the row can never receive a click at all (a `pointer-events: none` element is inert) — a self-contradiction caught before it shipped. The old `Table`'s actual mechanism (re-read `TableBodyRowCell.vue`, not just `TableBodyRow.vue`) is a full-size, clickable (no `pointer-events-none`) `RouterLink`/`button` repeated in **every cell**, positioned `absolute inset-0 z-0`, with that cell's own content wrapped in a separate `pointer-events-none relative z-1` layer stacked on top — content is visually on top but never intercepts clicks, so they always fall through to that cell's own catcher underneath. Ported the same way: `DataTableCell.vue` gained an `onRowClick` prop and the same per-cell catcher/content-wrapper split; `DataTableRow.vue` itself carries no row-level overlay at all. Cell types that render genuinely interactive content (none do today) would need their own `pointer-events-auto` layer on top, same as the old table's `TableBodyRowCellInteractiveElement` — not built, since nothing needs it yet.

### Inline action rendering — reused UIActionTrigger, did not hand-resolve Action fields
`Action.name`/`.icon`/`.isApplicable`/`.execute` all take a resolved `ctx: ActionContext`, built from `models`/`metadata` via the action manager store — resolving these by hand for a bare icon button risked subtly diverging from real menu behavior (`disabledReason`, `availableWhenUnauthenticated`, etc.). `ui/action-trigger/ActionTrigger.vue` already exists as exactly this primitive — a slot-wrapper around one `Action` that hands back `{ label, icon, isExecuting, canExecute }` and wires the click/execute lifecycle itself (same pattern `DataTableSelectionActionBar.vue` half-reimplements manually) — `DataTableRowActionsCell.vue`'s inline icon buttons wrap each `Action` in `UIActionTrigger` rather than reading `action.icon?.(ctx)` etc. directly.

### Trailing actions column — hand-appended, non-TanStack track, not a real pinned column
Mirrors the leading checkbox/expand columns, not `DataTableColumn.isSticky: 'right'`'s real-TanStack-column-pinning path. The old `Table`'s own actions cell (`TableBodyRowActionsCell.vue`) is also not part of its sizing system — plain `sticky right-0` CSS, no reserved grid track — so the simpler, established precedent won over "more correct" reuse of the general pinning system, which would have needed a synthetic `ColumnDef` and guards to keep it out of resize/reorder/visibility. Width is a constant (`DATA_TABLE_ACTIONS_COLUMN_WIDTH(_PX)`), always appended to `gridTemplateColumns`'s trailing side once `row` is configured at all (not per-row) — `rightStickyOffsetPxByColumnId`'s cumulative math now starts past this column's width so a right-pinned data column never sits underneath it.

### Column priority / responsive hiding — designed (Phase E grilling), not yet built
Confirmed the old `Table` never had this either — not a port, a wholly new feature — and the new `DataTable` still has zero real consumers, so this was planned but deliberately left unimplemented pending an explicit go-ahead, unlike [[Sub component on mobile — implemented (Phase E)]] which was built in the same session. Decisions, once it's picked up:
- **Hidden = removed from the grid entirely** via TanStack's real `columnVisibility` (already wired end-to-end in `useDataTable`, sitting idle at `{}` — no overflow-indicator UI, which would be a materially bigger feature with no precedent in this codebase to build from).
- **Trigger = DataTable's own container width**, not viewport — consistent with the existing `@container/data-table` mobile-breakpoint convention, but that CSS query exposes no width value to script, so a new `ResizeObserver`-based composable is needed; no existing width-tracking primitive in `data-table/` can be reused as-is.
- **Checkbox/expand leading columns and pinned (`isSticky`) columns are both permanently exempt** — never real TanStack columns in the first case, and an explicit consumer signal ("keep this in view") in the second; only unpinned real columns participate in hiding.
- **New `priority?: number` field on `DataTableColumn`** (higher survives longer; ties fall back to right-to-left declaration order) — added as real API surface now rather than deferred, on explicit request, despite zero real consumers to validate the shape against.
- **Algorithm: greedy width-sum**, not per-column breakpoints. Considered a simpler per-column `hideBelowPx`-style breakpoint field instead — rejected because it can silently drift out of sync with a column's actual width after a resize, with nothing to catch the mismatch; summing real column widths against available container width can't drift by construction.

### Infinite scroll — implemented (Phase C)
`onNextPage?: (() => void) | null` on `DataTableProps`, triggered by a new shared composable (`useDataTableInfiniteScroll`) that ports the old `Table`'s mechanism verbatim — VueUse's `useInfiniteScroll` on the scroll container (`offset.bottom: 400`) plus a `watch(isScrollableVertically, ...)` immediate-fire fallback for a first page too short to overflow the container. Not wired per-virtualizer: the desktop flat and grouped virtualizer composables both run against the same DOM scroll element and only one is ever mounted at a time, so the trigger is called once per *real* scroll container instead — once in `DataTable.vue` (desktop) and once in `DataTableMobileList.vue` (mobile), each against its own element. Considered triggering off the virtualizer's own visible-range bounds instead of a raw scroll-offset threshold, but the scroll-offset approach needs no changes to the three existing virtualizer composables and matches proven old-table behavior, so it was ported as-is rather than redesigned.

### Loading / error / empty states — implemented (Phase C)
The vestigial `isInitialized` prop (declared, never wired to anything) is removed. In its place: `isLoading`/`isFetchingNextPage` (both render a ported 10-row skeleton, `DataTableLoadingRows.vue` — the former in place of absent rows, the latter appended after real ones), `error: ApiError | null` (replaces the row area with the `#error` slot or default `UIErrorState`), and an empty-state branch (`data.length === 0 && !isLoading && error === null` → default `UIEmptyState`, no slot override — DataTable has no filter/search prop surface to key a "no results" variant off of, unlike the old `Table`'s two-copy empty state).

### Selection + infinite scroll — select-all count display fixed; growing-selection semantics left as-is
[[Row selection state]] itself is unchanged — select-all still flips to `excludes` mode over whatever `props.data` currently contains, so rows that load after select-all was pressed are implicitly selected too (same behavior as the old table). Grilling this in Phase C surfaced that the actual user-facing problem isn't the selection *model*, it's the selection *count display*: the action bar showed `selectedItems.length`, which silently equals `props.data.length` during select-all and would visibly climb as more pages load in, with no indication it was never a stable total. Fixed with an optional `totalCount: number | null` prop — when set and select-all is active, the action bar shows `totalCount` instead of the loaded-row count. Whether select-all should *semantically* freeze to what was loaded at press-time, rather than grow, remains undecided — it just turned out not to be the thing that needed fixing right now.

### Known visual bugs, confirmed but not yet fixed
- **Double bottom border under grouping**: `DataTableRow.vue`, `DataTableGroupRow.vue`, and `DataTableSubComponentRow.vue` each declare their own `border-b border-secondary` unconditionally. The old `Table`'s equivalent row (`TableBodyRow.vue`) conditionally drops its own border via `!isGroupingEnabled` — DataTable has no equivalent conditional, so borders stack wherever two of these bordered rows sit adjacent (e.g. a group's last row against the next group header, or a sub-component row against the row below it).
- **Checkbox vertical misalignment**: `DataTableCheckboxCell.vue`/`DataTableHeaderCheckboxCell.vue` both use `h-10`; `DataTableGroupRow.vue`'s checkbox row is `h-9` — one row height off from every other checkbox context, breaking alignment between a group header's checkbox and the data-row checkboxes directly beneath it.
- **Header not sticky**: the header rowgroup and body rowgroup are siblings inside one `overflow-auto` container (`DataTable.vue`) with no `sticky top-0` on the header. Fixing this will interact with [[Sticky columns — currently first/last only, by boolean, not by arbitrary key]] — a sticky corner cell (pinned column × sticky header) needs `z-index` layered above both simultaneously, which `DataTableHeaderCell.vue` only partially anticipates today (`z-2`/`z-40` are scoped to resize-handle hover, not to a header-is-sticky-too scenario).

### Sub component on mobile — implemented (Phase E)
Shares the existing expand chevron/state with `hiddenCells` (see [[Mobile slot]]) rather than getting a second trigger — one expand affordance per card, matching desktop's one-expand-per-row model, not two competing ones. Chevron visibility is per-row OR logic — `hiddenCells.length > 0 || subComponent(item) !== null` — mirroring desktop's `canExpandSubComponent` already being per-row; a card with neither shows no chevron. No new expand-state Set needed — mobile already had exactly one expand-state concept per card.

First shipped version showed `hiddenCells` and `subComponent`'s content stacked together in the same expanded area whenever both existed for a row — reported as looking wrong immediately after shipping. Corrected: `subComponent`, when present for a row, **replaces** `hiddenCells` entirely for that row rather than appending to it — it's a deliberate, curated view (same as desktop's sub-row), not extra content meant to sit alongside the generic unslotted-column dump. Rows with no `subComponent` still fall back to the plain `hiddenCells` list exactly as before.

### Mobile expanded-card content — reworked into one bordered card with an attached footer
The expanded area (`hiddenCells` list and/or `subComponent`) originally reused `UIDetailListGroupItem`/`DetailListGroupItemLabel` with no borders or dividers between rows, which read as a flat, ungrouped stack — reported as looking weird. Considered reusing `UIDetailListGroupItem` with `horizontal-value-alignment="end"` plus a manually-added bordered wrapper, but settled on fully custom markup instead (plain `div`s, `rounded-lg border border-secondary divide-y divide-secondary`, one `flex justify-between px-md py-sm` row per cell) since none of the detail-list primitives provide the bordered/divided-card look on their own anyway, and going custom keeps direct control over each row's exact spacing/typography instead of fighting `UIDetailListGroupItem`'s built-in responsive vertical/horizontal switch, which this context doesn't need (mobile-card width is fixed, not variable). Cell values still render through the same `DataTableCellRenderer` used for the table's own cells — a `badge`/`timestamp`/`text` value doesn't need different markup just because it's in a label/value row instead of a grid cell.

This is unrelated to `DataTableCustomCellConfig.detailListComponent`, which is still unwired anywhere in the codebase — that field is for a custom cell's appearance in the mobile card's 4-slot row (primary/secondary/meta/indicator), not the `hiddenCells` list, which intentionally keeps using `cellComponent` (the same one the desktop table cell uses) since there's no reason a hidden-cell value should look different there.

The "View details" button and row-actions `⋯` menu were also missing on mobile — `DataTableMobileList.vue` only ever extracted `.onClick` from the resolved `DataTableRowConfig`, never `.actions`/`.model`. Fixed by threading `inlineActions`/`moreActions`/`model` through the same `rowConfig` computed already used for `onClick` (mirroring `DataTable.vue`'s desktop `rowConfig` pattern), and adding a `UIActionDropdownMenu` next to "View details" in `DataTableMobileCard.vue` — merging `inlineActions`+`moreActions` into one `allActions` list behind a single `⋯` trigger (same `allActions` merge pattern as desktop's `DataTableRow.vue`, but unlike desktop there's no separate row of individual inline icon buttons — mobile has no room for that, so everything funnels into one dropdown). Initially placed as a standalone row below the bordered card, which read as randomly floating and disconnected; fixed by moving both buttons inside the same bordered container as the last divided row, so the whole expanded area (fields + footer actions) reads as one cohesive card.
